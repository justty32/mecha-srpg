# 派線教訓（一）：領導、等待與分工

[lessons 索引](lessons.md)｜[dispatch](README.md)

以下四條來自 `moddings/skyrim` 的 `wf/lessons/dispatch-*.md`（2026-08～10 實跑），只留跟 Skyrim 無關的通用部分；本專案尚未重現，碰到了再補本專案的日期與證據。

## 5. 領導不可用「結束回合」當等待

skyrim 2026-09-06：三個 Opus 領導在等工人或等鎖時「結束回合、掛背景 watcher」，watcher 觸發後有時醒、有時不醒；其中一個從 16:52 卡到 18:59，最後停掉、開新領導用現成的 plan 十分鐘做完。原因：子 agent 結束回合後，後續訊息只在下一個 tool round 送達，沒有 tool round 就永遠收不到；背景指令完成的通知也不保證叫醒它。

**對策**：交接書與派領導的 prompt（現行模型見 [team-model](../team-model.md)；以下輪詢適用外部線，原生子 agent 用工具等待回傳）寫死「等待一律**前景** `until` 迴圈或 `wf/tools/inbox_poll.sh <我> --wait --timeout 540`／`wf/tools/cx_watch.sh … --timeout 540`，沒等到就再跑一輪」。頂層看到 `handoffs/STATE.md` 超過 20 分鐘沒動、也沒有 commit → 直接停掉它，開新領導接手。等「另一條線先完成」時，交接書要寫可驗證的完成判準、逾時上限與逾時後怎麼回報。

## 6. 子 agent 的 REPORT 要寫檔

skyrim 2026-10-03：多條 Claude 子 agent 線把整份 REPORT 塞回覆、不寫檔（子 agent 預設指示「不要主動建立報告檔」與交接書衝突），頂層只好代存，每份燒數 k token。

**對策**：交接書「交付」段明寫「**REPORT 是交付物，直接寫檔到 `<絕對路徑>`**，回覆只要 5 行摘要＋路徑」。仍被擋時頂層代存摘錄版即可，不必逐字。

## 7. 多信任 codex，少微管理

skyrim 2026-08-20：頂層把 codex 當 Sonnet 用——自己重算它報過的每個 hash、每幾十秒看一次畫面、交接書寫到一百多行、每批做完都要回來派下一批——幾分鐘燒掉六成額度。使用者原話：「你應該多信任他們一些，gpt-sol 是僅次於 opus 的一線模型，除了會彎彎繞繞之外沒啥問題。」

**對策**：一次給**整條線**，不拆批；不重算它已附證據的數字（抽驗一次建立信任即可）；不主動輪詢畫面，等終局信或 `cx_watch.sh` 事件；交接書寫護欄與驗收就好，不必寫死每一步。它唯一要壓住的是「為了保險亂跑驗證」，用「驗收就這幾條，做完就停」解決。判斷密集、產出是程式或資料表的線，另配一條**不讀實作的獨立覆核線**自己重跑驗收。

## 8. 頂層要用自己的助手

skyrim 2026-08-30：使用者說「你作為頂層 agent，做太多事情了」——頂層明明可以開私人輔助者（沒指定就兩個），卻一個都沒開，把資料合併、驗收腳本、跑測試、整批文件都自己做了。根本問題不是手癢，是**忘了自己有外包的權限**。

**對策**：開場就開助手，優先用 codex 線（不編團隊，終局直接進 `wf/inbox/new/`），原生子 agent 則用工具回傳，通訊方式不依模型決定。**外包**：合併資料、驗收腳本、跑測試、查 git 狀態、把已定結論落成文字、修連結。**留給自己**：仲裁矛盾、資源與授權分配、範圍裁定、對使用者說話。判準是「這件事需要我的判斷，還是只需要有人動手」。不是每件事都要開團隊：單一、有界、驗收寫得死的工作直接開一條 codex 線掛在頂層底下。
