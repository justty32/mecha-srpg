# 審查與驗證

[組織草案](../README.md)

## review：獨立審查

職責：審指定基準與候選版本的 diff，優先看正確性、規格越界、重播確定性、資訊遮罩、層間依賴及測試是否能抓錯。不自行修補被審程式，不以 lint 代替審查。

讀寫範圍：唯讀候選程式、測試與契約，只寫指定 REPORT。不得更改測試讓它綠燈。共置單元測試由作者線維護；qa 要新增案例時，先由 lead 給該檔獨佔權，不建立永久雙重寫手。

交接：DONE／FAILED 給 lead，附檔案行號、問題、重現或推論依據、嚴重度；無發現明說並列剩餘風險。Done when: 每條驗收及阻擋項有結論，審查對應的版本明確，且 reviewer 不是本批作者。

模型：gpt-6.1-sol；high 作為可用 runtime 支援時的建議，不假設 endpoint 名稱等於 CLI 型號。

## qa：回歸與試玩

職責：排定驗證、分析失敗、維護回歸案例；固定指令直接交工具執行，不另開只會轉述退出碼的 agent。機器測試與使用者實機評閱分開。

讀寫範圍：唯讀候選程式；寫當次明列的 e2e／test 案例與 REPORT。變動原始碼由 dev 修；營運或世界內容變動須照現行規則在同一 commit 重錄黃金並寫原因，不以 qa 名義放寬。既有 test-prune 線持有測試領地，派線前先確認是否仍在役。

交接：給 lead 指令、版本、退出碼、證據路徑、seed／操作序列及未跑／不能跑／不適用的區別。有產品缺陷 FAILED；環境卡住 BLOCKED；需要裁示 NEEDS-USER。Done when: brief 固定驗證項有結果，失敗有缺陷報告；只有所有必要項通過才可放行，報告完成不代表品質通過。

模型：一般驗證判斷 gpt-6.1-sol；**headless 試玩必須由 gpt-6-astra 負責，同時僅一位**（現行 11/18 裁示），不能照 arena 把所有 qa 都設 sol。畫風、手機手感、真實畫面仍由使用者確認。

所有 node／npm 工作由 lead 協調全機序列執行，常駐 MCP 例外。現有 scripts/heavy-lock.sh 鎖的是 git common dir，只能互斥同 repo／worktree，不能證明跨 repo 全機互斥；正式啟用前需與 eca_main 協調全機排程，不直接複製 arena 的私有鎖或工具。不得停止使用者的 Vite。
