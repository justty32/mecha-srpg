# STRUCTURE — 結構整理參考（被動 / 按需取用）

[INDEX](INDEX.md)｜派發 [WORKFLOWS](WORKFLOWS.md)

**被動參考**：只在你要**重構 / 整理結構**（拆大檔、分類雜亂資料夾、長出新工作流、清掉過時文檔）時取用。本檔是專案組織原則的**唯一出處**，其他檔只連過來、不重述；always-on 鐵律在 AGENTS.md。

---

## 分層原則

1. **分層樹**：整個專案文檔是一棵樹，每層**只指向下一層、不存下層細節**：
   ```
   AGENTS.md（最頂，薄路由器）→ WORKFLOWS.md（依意圖派發）/ INDEX.md（結構地圖）
     → 各工作流入口（README 或單檔）→ 工作流內容 → 子工作流…
   ```
   往下走才找細節；下層檔**不向上連 AGENTS.md**（也讓非侵入式佈局自然成立）。
2. **檔名語意**：**README**＝初入一個資料夾先讀的入口／導引；**INDEX**＝描述該資料夾頂層結構的索引。小資料夾兩者合一，大了才分出獨立 INDEX。
3. **durable 知識歸層**：每份長期知識歸到它所屬的那個工作流／那一層，**絕不往上堆**——AGENTS.md 因此永遠很薄。
4. **活狀態只列 open**：進度記 `SESSION-LOG.md`、等使用者的記 `WAIT_USER.md`，**完成即刪**；「改了什麼」交給 git log，「為什麼這樣選」記 `workflows/decisions.md`。`SESSION-LOG.md`、`WAIT_USER.md` 各 ≤ 4096 bytes；超過代表有已完成的項目沒刪，先刪再說，不要拆檔。
5. **鐵律極少而 always-on**：3–5 條任何時刻都適用的規矩常駐 AGENTS.md，其餘一切按需取用。

## 結構整理原則（膨脹即拆 / 雜亂即分類）

兩個觸發、同一套方法：

- **觸發 A：單體過大**，客觀門檻依內容性質分套：
  1. `workflows/` 流程文檔單檔 > **8192 bytes**（操作筆記性質，bytes 逼它精簡；`wf-lint` 會掃）；
  2. 使用手冊 / 產品文檔單檔 > **300 行**；
  3. 程式碼單檔 > **300 行**；
  4. **條列式區塊 > 1024 bytes**（表格／清單，每列同一組欄位）→ 抽成資料檔，不管整檔多大；連結表另計：**考慮使用者**——給人點的留 md、給 AI 讀的進資料檔，所以連結表不看 bytes，超過**十條**才考慮，且先看用途——給人導航的（路由表、目錄表、派發表）留 md 走一般 8 KB 上限（超了就分層，上層只列子層入口），給 AI 消化的（候選表、ledger 裡的連結欄）才抽資料檔；
  5. 一個資料夾裡 **< 1 KB 小檔太多** → 合併（內容保留、原檔消失）。

  門檻是**觸發檢視的訊號**、非硬性上限：本質不可分的單體（一份完整 spec／plan、一篇連貫的調查筆記）可超標保留；**已完成的 spec/plan 併入 `specs/core` 等現役契約後刪除**。
- **觸發 B：資料夾雜亂**：一個資料夾裡散落**不同用途**的檔案，混在一起難導航；**同類檔案**（同一系列 log／報告）可以放鬆，不必為了檔數硬拆，不同用途混放才拆。


方法（兩種觸發都照做）：

1. **按內容／職責／用途語意分**，不是硬切等分——每塊要有單一清楚的職責。
2. 放進**專屬子資料夾**（或既有領域檔）依用途歸類。
3. 子資料夾頂層留 **README / INDEX** 做導航，已有就更新。
4. 原位置只留**精簡指標＋指向 index 的連結**，不再塞細節。
5. **整檔 >8 KB 拆資料夾時原路徑保留當入口**（外部連結不斷）。

## 一個工作流的成長軌跡（四級）

工作流**按需要逐步長出來**，每升一級都是「膨脹即拆」的套用：

1. **單檔**：一個 `.md`，**檔名即其意義**（如 `testing.md`），導引、結構、內容揉在一起。最輕量，多數工作流停在這。
2. **資料夾＋單 README**：膨脹到要拆 → 變資料夾，裡面**只有 `README.md`**，仍一肩扛導引＋細則＋結構。
3. **資料夾內不只 README**：README 再膨脹 → 拆出獨立檔各司其職：`INDEX.md`（結構）、`session-log.md`（本工作流 open 進度）、`gotchas.md`、內容檔…，README 退回只做「先讀我」。
4. **資料夾內有子工作流**：大到內部得再開巢狀工作流，各子工作流自己又從第 1 級開始長。

走到哪一級由「是否膨脹 / 雜亂」決定，不預先過度設計。**降級也成立**：子項消失就往回併級。

## 工作流的統一形式

- **入口檔段落**固定，照 [workflows/TEMPLATE.workflow.md](workflows/TEMPLATE.workflow.md)：何時用 ↔ 何時不用 / `Done when:` / 流程 / 交接。
- **`Done when:` 只准三類可觀察條件**：檔案存在、指令回傳、表格填滿（✗「功能做好」這種不可觀察的）。
- **資料夾型**：入口 `README.md` ＋視需要的 `gotchas.md`、`session-log.md`；**單檔型**：一個 `.md` 同時是入口與內容。有哪些工作流看派發表。

## 過時就刪（git 歷史即封存）

- 過時或被取代的文檔直接 `git rm`，**不再搬進 `archive/`、`done/`、`superseded/`**。commit 訊息第一行寫 `docs(tidy): 刪 <路徑>，由 <取代者> 取代`；沒有取代者就寫原因。
- 活文件裡指向被刪檔的連結要拿掉，改成純文字或刪掉那句；要追溯就寫 commit hash（刪除前最後一個含它的 commit）。資料檔的來源欄同樣改成「線名＋commit」純文字。
- 刪之前先確認沒有活文件**照它做事**（工具、護欄、契約）：有就先把精簡結論併進該去的工作流或 spec，或把工具搬到 `scripts/`。
- 以後不再建立 `archive/`；inbox 的 `done/` 只留本機、不進版控（已辦的證據是 commit）。dispatch 交接書與報告的收線與保留期見 [dispatch/handoffs](workflows/dispatch/handoffs/README.md)。

## 資料檔慣例

抽成 `.json`／`.csv` 的門檻與格式契約 `wf-table/1` 在 [workflows/common/data-files.md](workflows/common/data-files.md)；讀寫走 `tabledb.py`；整理流程走 [workflows/tidy/README.md](workflows/tidy/README.md)；json 內跨層路徑可用 `$fmt` 代號（見 [data-files-fmt](workflows/common/data-files-fmt.md)）。

**生成式資料索引**：由工具從來源檔產生的索引（例：`content/index/`，`npm run content:index` 重建）只從來源檔重建、不手改、進 git；驗證時重建結果與 git 版本比對不過就擋下（`npm test` 的索引一致性）。
