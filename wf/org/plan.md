# 落地計畫與適用邊界

使用者已授權規劃後開始使用；現採最小按需啟用，執行證據見 [啟用記錄](activation.md)。以下方案比較保留作設計理由，不再把整體組織採用列為待核准。

[組織草案](README.md)

## 方案與取捨

建議採「main＋按批次 lead＋按需專業線」。保留 mecha 三層規則與內容護欄，增加 arena 式的職責／交接清晰度；不讓 main 同時盯所有工人。代價是每批仍須寫 brief 與分配領地。

不建議直接常駐 design、dev、qa、review、integration 五個部門：本專案全機 Node 只能一次一個，多程序不會提高測試吞吐，而且多了一層閒置監看。也不建議只開泛用 dev 一線包全部：內容、共享契約、試玩與獨立審查需要不同邊界。

先不設 kb、獨立 integration 或自治改進任務；只有實際反覆出現維護需求才提案。arena 的部門自治、空閒自建工具、留言板、唯一提交口、只有 main 是 eca 等授權，都不是 mecha 的既定授權。

## 啟用時的選擇與保留事項

專案 main 保留直接對話入口，跨專案資源與彙總送 eca_main；本專案決策仍由 main 記錄。工人沿用 codex 偏好，本次獨立唯讀 reviewer 用 agent-fsm／sol，並不推廣成所有工人必須 fsm。

提交規則不變；本次 brief 明定不 commit／push。未來需要整批單一提交者時，在當次 brief 指名 lead，不藉本次啟用新增永久 integration 權限。

全機 Node 排程由 eca_main 協調共同機制；尚未確認前只做靜態工作，不宣稱 repo 鎖滿足全機限制。這是保留的執行限制，不阻擋唯讀審查啟用。

模型角色預設不需重訂；工具中的 endpoint／CLI 型號如何落實仍要驗證。第一輪建議一個 lead、一條 dev 寫入線，review 按需開，qa 需要試玩才開 astra；並行靜態工作可增加，但不增加 Node 並行量。

## 分階段步驟與驗證

### 一、確認現役工作與基準

main 先向原線確認 CLAIMS 與 dirty 檔的擁有者，選一個已核定且不碰其領地的小切片，不自行接手 SESSION-LOG 的舊工作。記錄基準 commit、候選差異及明列可寫路徑。

驗證：每個可寫路徑只有一位持有人，brief 明列禁止項、資源、固定驗收、模型、通道與子代理上限，brief_lint --strict 回傳 0。

### 二、對齊文件與定義

main 根據裁示同步 team-model、dispatch、inbox 及 CLAIMS 的委派規則；保留規格、manifest 與 backlog 原位置。用 agent_def 建工作區定義，逐一 check；依 body 設最少工具，無需要就不給下屬擴權工具。

驗證：文件不互相矛盾；每個 check 的 problems 空；使用明確模型做只讀小任務並有終局回報，不以 check 成功代替模型可用性證據。失敗即報告，不改模型偷渡。

### 三、試行一批

lead 派單一作者，review 獨立審查；qa 僅跑 brief 內必要項。測試前確認全機序列資源，所有證據綁定同一候選版本；修正後重驗受影響項。沒有實機評閱不能宣稱畫面／手感通過。

驗證：作者與 reviewer 不同；驗收有退出碼和證據路徑；沒有越界修改；必要黃金與內容閘門未被跳過；提交只含明列檔案，使用者既有 dirty 檔未被混入。

### 四、收線與回顧

lead 核對終局、整合範圍、子 agent 清理與剩餘待決事項；main 回報 eca_main。若單批證明協調成本低且領地可獨立，再增加靜態作者線；若重複改同檔或測試排隊未改善，就縮回單線，不為組織完整硬開人。

驗證：自己開的 subagent 已移除，有回報與實際結果；WAIT_USER 只留真正等使用者的 open 項，SESSION-LOG 完成項已移除。文件部署後跑 wf-lint --strict，現存問題與本批新增問題分開列。

## 啟用範圍

本次建立唯讀 review 定義並做交接實測；不遷移資產、不改原始碼、不 commit／push、不接手既有試玩或測試刪減工作。正式遊戲切片仍須明確任務、領地及全機資源協調，不能用本次組織授權替代。
